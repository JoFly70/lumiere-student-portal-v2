## The hosted staging gap

No isolated hosted non-production environment exists in this container. The only connected hosted DB credential is a Neon project named `clientdesk-production`, which belongs to a different application's production and must not be touched (it was not). No Supabase staging credentials are present. Consequently nothing here proves: real Supabase Auth emails and redirect behaviour, real JWT validation, RLS under real roles through PostgREST, real Storage signed uploads, real SMTP/email, hosting env-var wiring, or the live Meta model call. Closing the gap requires creating a staging Supabase project and a staging deployment, then re-running this table against it.

## Deployment prerequisites (all hosted work still to do)

1. **Staging first.** Create an isolated Supabase project; do not reuse any production credential. Repeat this table there.
2. **Pre-existing schema.** The target must already contain the S14 account gate (`account_invitations`, account status), the support tables, and the S09/S11 high-school schema. These are not in `supabase/migrations/` (see `migration-verification.md`). Run `scripts/release/s14` probes first.
3. **Migrations, in this exact order, none skipped:** `20261030100000_s18_billing_ledger`, `20261030100100_s18_billing_audit_event_types`, `20261030110000_s18_document_student_message`, `20261031100000_s19_ticket_comment_idempotency`, `20261031110000_s19_billing_corrections`, `20261101100000_s20_billing_evidence_void`, `20261101200000_s20_assistant_usage`. Apply before deploying the code. Each is idempotent; the two enum files use `ADD VALUE` and must stay separate files.
4. **Environment variables (server):**
   * Existing: `SUPABASE_URL`, `SUPABASE_SERVICE_KEY`, `DATABASE_URL`, `SESSION_SECRET` (must be set; the dev default is only for local JWTs and local JWTs are disabled when `NODE_ENV=production`), `NODE_ENV=production`, `APP_URL` (the public https origin; used for verification and reset links), `ALLOW_DEMO_MODE` unset.
   * `ENABLE_EMAIL_VERIFICATION=true` so newly invited accounts are created unconfirmed and must verify.
   * Academic Assistant (all optional; absent means safe defaults): `SPARK_ASSISTANT_ENABLED` (default **false**; only the literal `true` enables live inference), `META_MODEL_API_KEY` (**server-only secret**; never `VITE_`-prefixed, never in client code or logs; no key means the assistant stays off), `SPARK_ASSISTANT_LIVE_ROLES` (default empty; `student` is never honoured), `SPARK_ASSISTANT_MONTHLY_BUDGET_USD` (default 2), `SPARK_ASSISTANT_MAX_INPUT_TOKENS` (2500), `SPARK_ASSISTANT_MAX_OUTPUT_TOKENS` (700), `SPARK_ASSISTANT_TIMEOUT_MS` (15000), `SPARK_ASSISTANT_RATE_LIMIT_PER_MINUTE` (6). Router mounted at `/api/assistant`.
5. **Supabase Auth settings:** enable "Confirm email"; Site URL = `APP_URL`; add both `${APP_URL}/auth/verify` (existing signup emails) and `${APP_URL}/verify-email` (used by the resend endpoint) to the Redirect URLs allow-list; both routes render the same server-verified page; confirm the signup email template links back to that URL with a `token_hash` or access token. Run `npm run verify:supabase-auth-config` against staging.
6. **Smoke after deploy (staging, then production):** one synthetic invited student through J1 to J15 by hand, plus `scripts/release/s14/smoke-hosted.sh` read-only probes. Confirm assistant returns its disabled state while `SPARK_ASSISTANT_ENABLED` is unset.
7. **Rollback:** the migrations are additive; S20 billing migration replaces one index (re-creating the old all-rows unique index would fail if a voided and an active receipt now share an evidence_id). Code rollback with migrations left in place is safe for #1-#5 and #7; for #6 the older code simply keeps the voided-evidence limitation.
