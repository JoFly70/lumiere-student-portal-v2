# First production student: admin setup workflow (readiness review)

Status: **READINESS REVIEW ONLY. NOTHING HERE HAS BEEN DONE FOR A REAL STUDENT, AND NOTHING WAS RUN HOSTED.** No real student data, price, date, elective name or payment appears in this document or in the repository; everything below that needs one is marked `<owner input>`. The steps were checked by reading the code (file and line cited) and, for the HTTP behaviour, by the local S21/S22 journeys (`tests/s21-journey-first-student.test.ts`, `tests/s22-hosted-journey-harness.test.ts`, both local PostgreSQL 16 with test doubles). A hosted rehearsal on staging comes first: `docs/recovery/s22/hosted-journey.md`.

Target: one student on the Standard U.S. High School Diploma, **21 credits = 16 core + 5 elective** (`shared/high-school-contract.ts:186-273`, template `us-hs-diploma-21` version 2).

## 0. Who can do what

| Role | Can | Cannot (by design) |
|---|---|---|
| Admin | Everything below | |
| Staff | Draft the roadmap, record results and reviews, billing (price, discounts, schedule, evidence, receipts), document review, support | Open `/admin` or the student workspace (`client/src/App.tsx:83,118`), create students, issue invitations, link accounts (`server/routes/admin.ts:23-24`, `admin-student-account.ts:122`), publish a roadmap, confirm graduation eligibility |

So the whole setup is an **admin** job; staff continue from step 6.

## 1. Preconditions

1. Production database and app are the ones you intend (not S22 staging). The first admin exists (nothing in the repo creates it: `docs/recovery/s21/staging-readiness.md:54`, `docs/recovery/S14-production-launch-record.md`): an auth user, a `public.users` row with role `admin` and a `profiles` row with status `active`.
2. `ENABLE_EMAIL_VERIFICATION=true` (J2 of the hosted journey asserts the account is created unconfirmed) and the e-mail path confirmed by hand: `docs/recovery/s22/auth-email.md`. Invitations are **not** e-mailed (below), so the invitation hand-off is manual either way.
3. The hosted journey has passed on staging (`HOSTED PASS` evidence file). Until then every step below is "possible in the code", not "proven hosted".

## 3. Gaps and blockers

1. **Blocker, hosted proof.** None of steps 1 to 12 has run on a hosted deployment. Run the hosted journey on staging, send back the evidence, then do the real student.
2. **Blocker, owner inputs.** Real student identity, the awarding school's elective offerings, price, currency, discounts, installment dates, start and target dates are not in the repository and must come from you. Nothing was invented.
3. **Gap, no staff upload.** The staff UI can view, verify and reject student-uploaded documents but cannot upload one on a student's behalf (no caller of the upload routes outside `documents.tsx`). The API allows it for staff (`server/routes/documents.ts:188`, staff schema and visibility in `server/services/document-service.ts:243-285`), so a school-issued document (enrollment agreement, acceptance letter, transcript) has to be uploaded by the student, or by an administrator through the API, until a screen is added. The Documents page itself accepts only PDF, PNG, JPEG and WEBP up to 10 MB (`server/lib/document-storage.ts`); the wider 8-format set is chat attachments only.
4. **Gap, student stays "Lead".** The Add student dialog creates status Lead and nothing in the UI changes it (the route exists, `server/routes/admin.ts:367`, with no client caller). No server gate on Lead was found, so it is cosmetic, but the Students list will show Lead.
5. **Gap, staff cannot start the workflow.** Student creation, invitation and account linking are admin-only (section 0). If staff are meant to onboard students, that is a product change.
6. **Gap, finding a student as staff.** The staff billing entry asks for the raw student UUID; there is no staff student search outside `/admin`.
7. **Check before publishing a real roadmap.** Template v2 core titles (Personal Finance, U.S. History, U.S. Government and Economics, Health and Nutrition) come from the school's public page "pending the school's written confirmation" (`shared/high-school-contract.ts:249-252`). Confirm them with the school first; the plan can be adjusted by a new draft but published versions are immutable.
8. **E-mail.** Verification and recovery e-mail delivery is not verified anywhere yet (`docs/recovery/s22/auth-email.md`); invitations are hand-delivered. Have a second way to reach the student.

## 4. Order of work

Staging rehearsal (hosted journey, then optionally this workflow by hand with a synthetic student) -> owner supplies the inputs in gap 2 -> steps 1 to 4 -> 5 to 9 -> 10 -> 11 -> hand the student their sign-in -> step 12 ongoing.
